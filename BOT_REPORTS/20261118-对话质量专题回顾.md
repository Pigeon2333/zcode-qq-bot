# ZCode QQ机器人 · 对话质量专题回顾（供更强模型复审）

> 写作日期：2026-11-18
> 范围：自项目开始（2026-10 末）至 v0.5.18 全部 392 commits 中，与「对话贴近真人、识图、上下文连贯、记忆、聪明程度、风格」相关的**所有问题与当时的解法**。已排除低级疏忽性 bug、纯性能/安全类修复。
> 写作动机：项目从单一聊天机器人长成多插件多后端的系统，对话质量修复方式是"出了问题→打补丁"。用户担心：①补丁之间相互影响（已出现过至少 4 次修复引入新事故）；②结构臃肿；③整体黑箱化——连开发者本人都不确定当前实现是不是最优解。
> **本文目的：留档待审。等 GLM-5.5 或更强模型上线后，把本文 + 相关源码交给它，重新审视每个问题的解法是否最优、是否该合并/重构/推翻。**

## 0. 系统现状速写（复审者必读）

- 四进程桌面应用：qq_app（外壳）→ qq_admin_ui（:39765 管理台）→ qq_daemon（:39763 消息管道）→ qq_bot_agent（:39764 大脑）。协议端可插拔（napcat / llonebot，v0.5.18 起）。
- 模型链：glm-5.3-flash（日常）→ glm-5.3 → glm-4.7-flash → … 多级降级 + key 池轮换 + 200s 预算熔断。视觉单独配模型（glm-4.6v）。
- 上下文构造（build_messages，~2900 行文件中的核心函数）：system = 全局设定+人设栈+风格卡+自进化观察+记忆 snippet+跳过守卫+防滥用+画图规则+表情包菜单+语音规则+表情回应规则+群管边界+群管理能力教学(仅主人)…；user = 场景+最近对话(带时间戳)+历史注解+对话关系判断+【现在】行+引用原文。
- 消息管道：ws 事件 → 段解析(text/at/image/face/mface/json/reply/forward/record/未知段) → 触发判定(标准/关键词/闲聊骰/at/reply_to_bot/all_prob 图) → 收件箱 → agent 处理(gate→视觉→文本链→出站 parse_reply) → daemon 发送队列(限流/拟人延迟/去重/标记拦截)。
- 出站防线已叠五层：parse_reply 标记剥离 → daemon _MARK_LEAK_RE → 行首[]元数据(逐行) → 占位复读剥离 → 元指令句剥离。另有追聊回声词表、dedup（会话/全局双闸）、时间前缀清洗、连贯性守卫。
- 插件宿主：on_tick/on_message/on_observe/inject_context/route/store/send/send_image/send_voice/every，市场插件 11 个。

**复审要点：以上每一层都是"补丁层"——它的存在理由、相互依赖、能否合并，是本次复审的核心问题。**

## 一、真人感 / 语气自然度

### 1.1 「人机感」的系统性抱怨（2026-11-10 复盘）
**问题**：群友反馈"越来越没有活人感"。复盘定位五个根因：①能力型接话过密（看图+引用兜底+卡片解析让任何消息都有得接，空占位硬回复 N 次/3天）；②回复结构模板化（先复述对方一句+展开两行的固定节奏）；③能力教学段挤占人设表达空间（system 里教学累计 2-3k 字符）；④回指过多（"我记得你上次…"档案感）；⑤识图错认。
**当时解法**（P1/P2/P3/P5，全可配置）：
- P1 空占位降级：纯图/表情 → 表情回应或跳过（blank_img_policy 三档）
- P2 克制总纲："大多数消息只看不说""能力只在对方明确需要时用"
- P3 闲聊长度上限：超 80 字带指令重写压缩（非硬截断）
- P5 回指限制：不主动引用超 3 天前的记忆
**复审问题**：
- 这些全是"减法补丁"——抑制机器人的表达欲来换自然度。有没有更好的正路？例如：把"该不该接、接多深"交给一个统一的"社交判断模型调用"而不是十几条独立骰子/gate/冷却？
- chat_max_len 的"带指令重写压缩"多花一次模型调用且可能丢信息——是否该在生成时就把长度感知放进 prompt（而非事后修剪）？
- P2 总纲与 P5 回指限制与人设卡的关系：风格约束曾按用户原则"走人设层不走底层"，但 P2/P5 走了底层——两类约束的归属边界已不一致，需要统一原则。

### 1.2 括号动作 / emoji 泛滥
**问题**：模型每句带 emoji；人设自带"（小声）"示范+flash 戏剧腔导致括号动作泛滥。
**当时解法**：emoji 走底层硬规则 → 用户否决（底层只放安全规则）→ 改写进全局通用设定；括号动作走人设卡约束。原则确立："底层 prompt 只放安全性规则，风格类约束放人设卡由用户自选"。
**复审问题**：这个原则后来被反复打破——群管边界、克制总纲、时刻保密、防插嘴教学都进了底层 system。原则本身是否还成立？"安全 vs 风格"的分类法在"群管理边界"这类语义模糊的规则面前失效了。需要重新定义分层准则。

### 1.3 时刻保密 / 时间感知
**问题**：机器人泄露当前钟点（"晚上八点"）显得像系统；主动消息在中午说"今晚早点休息"。
**当时解法**：时刻保密硬性规则（中文钟点全封，仅对方明确问才答）+ 出站时间前缀确定性清洗 + 历史行加[时:分]时间戳（模型有时间上下文但被禁止复读）。
**复审问题**："禁止报时"是补丁，正解可能是"时间只在被问/相关时才进入意识"——即时间作为检索线索而非注入常量。当前注入的【当前真实时间】块与保密规则互相矛盾（给了又禁用）。

### 1.4 表情包 / 表情回应
**问题**：表情包被当空消息；表情包发得不合适；满屏 emoji。
**当时解法**：占位符（[图片]/[表情]）入历史；表情包三层库（人设专属/通用/QQ导入）+发前视觉判断契合度+频率限制；[STICKER:n] 标记协议；表情回应（set_msg_emoji_like）语境化挂小黄脸。
**复审问题**：表情包选择是"视觉模型看懂→判断契合"两跳——成本高且判断质量依赖视觉模型。真人选表情包是条件反射，是否有更轻的路径（如"场景→表情包"的嵌入检索）？

### 1.5 追聊（nudge）
**问题演进**：①套话引导("调侃对方跑路了")→改场景判断框架(A/B/C/D)；②人设正文注入为空（persona_stack_text 读错键）致文案突兀；③双向判定差一错误（hist[1:] 误排）致两句对话永远漏追；④分类框架泄漏（"B类——"发进群）；⑤追聊在收尾语后追（晚安后又来一句）——"割裂感真因"；⑥群聊追问无门控在白名单外群也触发（潜伏）；⑦提示词回声（"换个新话头…像没事找话"整段发出）；⑧元指令句开头（"分析过程不外显，仅直接给出最终回复。"）。
**当时解法**：每次一个补丁——场景框架+回声词表扩词+出站元指令句剥离+跳过收尾语+群聊开关。
**复审问题**：追聊是历史上补丁密度最高的模块（8+ 补丁）。根因是"用模型生成一句社交消息"这个任务本身给了模型太多判断框架（A/B/C/D 分类、输出纪律、禁令清单），模型必然偶尔把框架当内容输出。**更优解可能是**：把追聊改成两段式——先用极小模型/规则选"追不追+追哪个方向"，再用极简 prompt 生成一句话（无框架无禁令）；或者干脆用模板库+人设变量（放弃每次即兴）。当前实现是"每句话都让模型即兴+怕它说错就加禁令"的死循环。

### 1.6 主动消息
**问题**：回复完 6 秒后又追加主动消息（体感复读）；深夜打扰；概率/间隔失衡；话题重复。
**当时解法**：3 分钟冷却门控；夜间静默+概率减半+间隔翻倍（风控分区）；分群计时+触发即记账；主题重复守卫（n-gram 重叠剔除）。
**复审问题**：主动消息的"该说什么"完全靠模型即兴+热点注入。真人主动开口有明确动机（看到相关的东西想起你/到点了/有事）。是否该给主动消息加"动机检索"（从记忆/热点/群历史里找真实由头）而不是纯生成？

### 1.7 括号 / 标记 / 元文本泄漏（贯穿性问题）
**问题全录**：[跳过]中文变体直发群友；[SPLIT]单括号变体；[语音][连线][STICKER][回应:id][GADMIN]旁路泄漏；[画:超长描述]300字击穿；时间前缀[21:05]句中/句首/第二行行首三种形态；[QQ表情#265]入站占位被模仿复读；"分析过程不外显"元指令句；追聊"B类——"分类框架；"tells me"英文蹦词；B站分享卡片占位被复读。
**当时解法**：出站防线叠了五层（见 §0）+ 每次泄漏加一条正则。
**复审问题**：**这是最需要重新设计的模块。** 当前模式是"泄漏→加正则"，本质是黑名单，永远追不上模型创造力。根本问题：模型的输出通道里混着"给用户的话"和"给系统的指令"，靠事后正则分离。**更优解**：①结构化输出——让模型用 JSON/工具调用返回{说给用户的话, 动作列表}，通道物理分离；②或"出站白名单"——回复只允许纯文本+有限个已注册标记，未知 [xxx] 一律拦（已有行首版，可全局化）。五层正则网可以合并成一个"出站净化管道"对象，每层可测试可配置。

## 二、识图 / 视觉

### 2.1 QQ 图床签名问题（171 次 400）
**问题**：NT CDN 图片带 rkey 签名只认 QQ 内部环境，模型服务端/外部 HTTP 一律 400"图片输入格式错误"。
**当时解法**：NapCat download_file 下载到 cache/images → base64 直传。后来加：缓存优先（命中零计数零下载）、日限 60→150、分钟限 10。
**复审问题**：①download_file 是 NapCat 扩展动作，换框架后识图整条链路不可用（已知，LLOneBot 场景未解）；②base64 直传成本高（每图 1-9MB 转码），是否有更省的通道（如公网图床中转）？③限频与识图质量的矛盾——"所有图都识"模式 60 次上午耗尽，提到 150 只是延迟矛盾爆发。

### 2.2 "明明有图却说没看到图"（贯穿五次修复）
**问题演进**：①QQ 把"图+文字"拆两条消息，文字条无图走纯文本链（遮光罩被当食物）；②同秒到达时严格 > 判断漏并；③回捞缓存"并入即 pop"被未触发的"继续"吞掉；④带指代词的追问（"这图怎么样"）无图可并；⑤视觉调用失败降级纯文本时，上下文里"图就在下方"提示成了谎言——模型一本正经说没图。
**当时解法**：合并缓存（90s→180s，只并入不删除，最多并 3 条）+ 同秒/先发图时序兼容（>= text_ts - 90）+ 历史回捞（指代词命中→捞 5 分钟内最近带图消息）+ 降级时纠正提示 + 视觉失败 all_prob 不骰点直接沉默（后来改裸@场景表情回应）。
**复审问题**：
- 当前的图文合并是一套**多规则状态机**（缓存 TTL/计数/时序比较/指代词正则/历史回捞/延迟 2.5s 向后等图/触发压制/重编号）——规则间交互复杂，已经出过"吞缓存"这种规则交互 bug。**更优解可能是**：把"最近 N 分钟本群所有带图消息"作为一等公民常驻上下文（图作为可引用对象带 ID），让模型自己引用"第 3 张图"，而不是靠规则猜哪张图属于哪句话。
- 指代词正则（继续/重试/这图/然后…刻意不含"什么/啥"）是启发式，必漏。模型侧解决（让模型自己判断"这句话在说哪张图"）可能比规则侧更准。
- 视觉失败时的"诚实提示"目前是文字注记——是否应该在视觉失败时根本不进入"有图"语境？

### 2.3 识图质量 / 接地
**问题**：识图信息量大→闲聊判定倾向有趣→几乎每图必回显突兀；小模型只按文字字面回复忽略图内容（遮光罩被当食物）；"这个/它"指代词被上文顶替；选民证被当结婚证。
**当时解法**：看图模式三档（all/all_prob/ask，all_prob 识图后单独骰点 30%）；接地指令（"这个/图中=图片主体"）；上下文提及图时跳过骰子；视觉模型专用化（glm-4.6v 替代 flash）。
**复审问题**：①三档模式+骰点+指代豁免+blank_img 降级+裸@降级——图相关决策已分散在 5 处，用户可配项膨胀。是否该收敛为一个"视觉策略"配置对象？②glm-4.6v 的识图质量天花板未测——错认（遮光罩→食物）到底模型能力问题还是 prompt 问题，没有做过系统评测（没有识图评测集）。

### 2.4 视觉链工程
**问题**：视觉链耗尽返回 None 解包炸；flash 模型看图跳过不冷却。
**当时解法**：异常化+key 池共用。
**复审问题**：视觉调用与文本链共用 key 池但视觉仅支持智谱——key 轮换语义不一致的问题仍然存在。

## 三、上下文连贯

### 3.1 说话人混淆（贯穿性问题）
**问题全录**：相邻不同人的话被合并回复（萨莉亚事件）；机器人回复叫错名字（yinkui 插嘴但回复带北柠名字）；群友互相"摸摸"被当成对机器人说；B 引用机器人回给 A 的消息，被当成 A 继续对话；纯@其他人的消息历史显示空行被评论"怎么发了个空白"。
**当时解法**：历史行加"名字(QQ): "前缀+显式教学（每行名字=说话人/相邻可能是不同人/回复前先看清【现在】行）；安抚词定向判定（摸摸→上一条说话人非 bot 则跳过）；@他人渲染进文本；引用 bot 自己的话时注入"引用者≠当时对话的人"。
**复审问题**：**这是最该被结构化解决但一直用文字教学硬顶的问题。** 当前历史格式是单行流水（"- [时:分] 名字(QQ): 内容"），对话的回合结构（谁在跟谁说话、引用关系、@关系）全靠模型从线性文本里推断+靠注入的教学提醒。**更优解**：历史注入结构化——消息带 reply_to/at 等关系字段（哪怕缩进或编号），让"谁在跟谁说话"成为数据而不是推理题。当前【现在】行+引用原文+教学是三段冗余信息，可合并成结构化对象。

### 3.2 上下文窗口管理
**问题**：注入截断致模型看不到热点清单尾部；长对话挤占；精简/全量档位黑盒。
**当时解法**：热点 _MAX 400→800；动态上下文预算（注入量感知双向自适应档位，升档直 jump 到 90k 档避免中间档无效）；档位文案明示。
**复审问题**：动态预算的"档位表"设计复杂（16/8 档 hist 相同导致升中间档无效的坑），守卫规则（fix_tok>窗口 55%→降档）与升档层曾连坐。**更优解**：按 token 计数直接计算预算分配（历史/记忆/教学的优先级装箱），而不是档位查表。

### 3.3 对话历史格式演化
**问题**：历史无时间戳→主动发言时间错乱（中午说今晚早点睡）；纯图/表情/语音历史空白被当空消息；合并转发只看到卡片壳；@他人空行；bot 自发消息双入史（发送入史+回显入史）被复读。
**当时解法**：时间戳前缀+占位符+转发展平（后台线程防 ws 死锁）+@渲染+message_id 去重+占位升级（回显带真实文本覆盖占位）。
**复审问题**：历史条目字段已经很多（ts/message_id/sender_id/is_bot/text/n_images/image_urls），但注入时全部压扁成单行文本。**结构化注入（§3.1）是统一解**。

### 3.4 引用/回复链
**问题**：引用无反应（Thread args 丢参事故）；引用旧消息 reply_text 空（装瞎）；引用图不可见；引用 BOT 自己的话换人混淆。
**当时解法**：get_msg 后台补查（array 形态 data.text 修复）；本地历史命中即用；被引图并入视觉；is_bot 提示。
**复审问题**：引用链现在有三条路径（本地历史/get_msg 补查/reply 段预览），三条路径的字段填充程度不一致——结构化后可统一。

## 四、记忆

### 4.1 记忆写入
**问题**：草莓糖张冠李戴（模型把 MCP 工具结果里的草莓新地记成主人喜好）；模型该记不记/不该记乱记。
**当时解法**：教学"只记对方亲口说的，推测/工具结果/自己的话不许记"+ [记忆] 标记协议 + [忘:关键词] 纠错（物理重写流水）。
**复审问题**：①记忆写入是"模型自愿输出标记"——没有写入队列/审核，写错靠事后纠错。**更优解**：写入前过一道轻量校验（这句话是谁说的、有据可查吗），或把记忆写入改为"候选→定期审核→入库"。②记忆条目无置信度/来源/衰减——所有记忆平等，旧错误记忆会一直被召回。

### 4.2 记忆召回
**问题**：黄仁勋瓜"总结里有、问它说没有"（注入截断+次日热点撤稿双盲）；回复频繁"我记得你上次"档案感。
**当时解法**：热点注入今天+近2天+提示"以这里为准别否认"；回指限制教学；记忆 snippets 按相关性注入（已有）。
**复审问题**：①记忆召回是"相关性 snippet"——相关性怎么算的（关键词？）没有系统评测；②"档案感"问题的本质是"机器人展示了它记忆的机制"——真人回忆是模糊的、带遗忘的。是否该给记忆召回加"模糊化/概率化"（不是每次都精准想起）？③长周期记忆（跨周/跨月）与短期对话记忆的关系没有设计——现在全部线性流水。

### 4.3 群成员画像
**问题**：画像数据是独立文件，与记忆流水分离；用户要求搜索功能。
**当时解法**：member_profiles 插件（默认关，隐私铁律）+ 双搜索框三档模糊。
**复审问题**：画像与记忆的关系（画像=记忆的聚合视图？）没有明确设计。画像更新时机、与对话中实际用法的联动未评测。

### 4.4 自进化 / 风格学习
**问题**：机器人说话越来越像出厂设置而非"群里的人"；风格约束放哪里反复纠结。
**当时解法**：style_learn 插件（全量观察→定期蒸馏成"观察"→注入 prompt）+ 风格卡按人设存储（_style: 键）+ 自进化注入条数可配 + 全局/专属叠加。
**复审问题**：①"观察"是自然语言句子注入 system——信息密度低（几条观察 vs 整个群的历史说话方式）；**更优解**：few-shot 示例（从群史挑 3-5 条该人设的真实回复作为风格示例注入）——当时没做是因为担心示例过时，但这可能仍是比"观察描述"更直接的风格传递。②蒸馏质量无评测——"像不像"没有量化。③风格学习的观察队列 2000 条环形，跨群混合——群特异性丢失。

## 五、"聪明"程度

### 5.1 热点/知识时效
**问题**：黄仁勋瓜否认事件（热点撤稿+只注入当天）；隔天问旧瓜不知。
**当时解法**：注入今天+近 2 天+指代词教学+"以这里为准"。
**复审问题**：热点是"注入文本"——模型无法主动查询更多细节。MCP/搜索有，但热点讨论场景没接。**更优解**：热点条目带来源链接，模型被问到时可以现场搜（工具化）而非依赖注入文本。

### 5.2 接梗/玩梗能力
**问题**：北柠"寄显卡打击黄仁勋"接不住（根子是不知道瓜的存在）；"原来我只是用来做实验的吗"这类反讽接得还行但依赖运气。
**当时解法**：热点注入修复后接梗自然改善；说话人对齐修复叫错名字。
**复审问题**：接梗依赖"知道梗的事实基础"——这是知识问题不是语气问题。当前没有"群内梗词典"（群友创造的梗）。记忆流水里其实有，但没有梗的提取/索引。

### 5.3 判断力（该不该说话/该不该做）
**问题**：对别人对话插嘴（多处）；纯图硬接；空@硬接；模仿主人指挥口头答应（cosplay）；对"导出"指令误响应。
**当时解法**：防插嘴三层（daemon 结构性拦截 peer_talk + gate 轻量判定 + prompt 对话关系判断）；安抚词定向；群管通用边界注入；裸@降级。
**复审问题**：**"该不该说话"的决策目前分散在：触发判定（daemon）→ botloop gate → 干兴趣判定 → 各种 skip 规则 → 模型 [跳过] 输出。五层决策，每层有自己的视角和盲区。** 更优解：收敛为"两级"——daemon 结构性硬规则（@/引用等确定信号）+ 一次统一的"社交语境判断"调用（把 peer_talk/兴趣/该不该接合成一个判断）。当前 gate 已经是轻量判定雏形，但只覆盖 chat_random。

### 5.4 模型能力天花板
**问题**：glm-5.3-flash 语气生硬（flash 戏剧腔）；指令遵循需要"必须"措辞；thinking 档输出配音稿式乱码。
**当时解法**：模型链降级+模型管理；连贯性守卫（乱码检测+纠错重试）；思考模式可配。
**复审问题**：①flash 的语气问题是模型能力问题——人设再好也压不住。GLM-5.5 上线后应重测"哪档模型在哪个场景性价比最优"，现在的链是按价格排的不是按"场景适配度"排的。②连贯性守卫的检测规则（meta 正则+≥5字片段×3）会漏新型乱码。

## 六、结构性担忧（用户原话的展开）

### 6.1 补丁的相互作用（已发生的实证）
- 引用图修复 → rt_note 漏默认值 → 全群失声（11-09 事故）
- 表情回应教学改造 → 模板 % 计数错 → 全群失声
- 语音规则插进拼接链 → build_messages 截断 → 0.4.3~0.4.4 全部对话失败
- 图文合并缓存 pop → 未触发消息吞图 → "有图说没图"
- 修 A 泄漏的正则误杀 B 正常话（"不要出现"口语句）
- Thread args 丢参 / ws 收线程死锁 / 裸 cfg——都是"修复路径引入新路径"的产物
**复审要点**：build_messages 和出站管道是两大多补丁交汇点。每次补丁的验证手段（py_compile/三场景冒烟/AST 检查）都是当时事故驱动的，没有一个"全量回归测试集"能跑"所有历史事故场景都还通过"。**建议复审者优先做的第一件事：把历史上所有事故场景固化成回归测试套件（估计 40+ 场景），之后再谈重构。**

### 6.2 结构臃肿的量化现状
- qq_bot_agent.py ~5900 行（大脑+教学+守卫+视觉+追聊+主动+devctrl+MCP+群管+记忆+…）
- qq_daemon.py ~2900 行（管道+触发判定+发送队列+群管钩子+框架分发）
- qq_admin_ui.py ~7900 行（全部页面+API）
- system prompt 由 15+ 段拼装，总长≈13k 字符（含人设/记忆/教学）
- 用户可配置项 60+（reply_config/app_config/群管/风控/看图模式/…）
**复审要点**：教学段是否可以分级注入（按消息类型只注入相关的）？60+ 配置项哪些实际被用户改过（数据在 plugins_state/app_config 历史里）——没人改的配置是否该固化为默认？

### 6.3 黑箱化
**现状**：排查靠"上下文注入日志"（ctx_*.jsonl）+ 运行日志关键词 grep——这俩是救命的，但只有开发者（AI 助手）会用。
**建议**：①对话质量的量化评测（像复盘报告那样定期跑，但聚焦"这周哪些回复不像真人"并归因到模块）；②关键决策点（触发/骰子/gate/降级）的决策日志结构化（为什么说/为什么没说，一行一条）；③给用户的"机器人当前行为解释"页面。

### 6.4 未解决 / 无最优解的问题清单（开放题，留给更强模型）
1. **"真人感"没有定义与度量**——所有活人感修复都基于用户主观截图反馈。是否可以建立评测（让 LLM 扮演群友盲测机器人 vs 真人消息）？没有度量就无法判断哪个方案更优。
2. **对话的结构化表示**（§3.1）——线性文本历史 → 结构化回合/关系。这是多个问题的共同根解，但改动面大（build_messages/历史存储/教学全要重写）。
3. **出站通道分离**（§1.7）——文本与指令的物理分离（结构化输出/工具调用式回复）。依赖模型能力（glm-5.3-flash 的 JSON 稳定性存疑，5.5 值得测）。
4. **记忆的生命周期**——写入校验/置信度/衰减/冲突合并/画像联动，当前只有"追加+手动删"。
5. **视觉策略收敛**（§2.3）——5 处图相关决策合一。
6. **识图评测集**——错认问题没有度量，换视觉模型全凭感觉。
7. **群内梗/黑话词典**——接梗能力的知识底座。
8. **主动消息动机检索**（§1.6）。
9. **多模型时代的策略**——GLM-5.5 上线后：模型链按场景适配重排？识图换更强模型？flash 的语气问题是否被新模型天然解决（从而可以删掉一批语气补丁）？**请复审者重点评估：哪些补丁在更强模型下会变得不必要**——例如教学类（说话人对齐/接地指令/克制总纲）可能被模型原生能力替代，而结构类（合并时序/缓存/标记剥离）仍然必要。
10. **NapCat 停更后的协议端风险**——已做 LLOneBot 切换，但 LLOneBot 缺公告/表情回应/识图三能力；是否值得为 llonebot 后端补齐这三个能力的替代实现（识图可走公网图床上传？）。
11. **风控的不可知性**——825 条款触发机制不明，现有缓解是猜测性的。腾讯服务端策略变化无法预知。
12. **成本**——token 消耗估算只覆盖固定注入；动态预算/视觉/重试链路的真实成本无监控面板。

## 八、给复审者的工作建议

1. **先建回归测试集**：把本文所有"问题场景"写成可自动运行的最小复现（估计 40+ 用例），这是任何重构的安全网。现成的骨架：BOT_REPORTS/_smoke_*.py 系列已有 60+ 用例散落，可归并。
2. **读码顺序**：qq_bot_agent.py 的 build_messages（上下文构造全貌）→ process()（决策全貌）→ qq_daemon.py 的 _decide_trigger + _send_one/_strip_control_marks（管道两刃）→ qq_bot_agent.py 出站段（parse_reply→五层防线）。
3. **重点权衡题**（本文各节"复审问题"的汇总）：结构化历史 vs 文字教学；出站白名单 vs 黑名单五层；记忆生命周期；活人感度量；补丁在更强模型下的存废。
4. **约束提醒**：用户原则（底层 prompt 只放安全规则/高危双确认/隐私默认关/攒批发版）——重构方案不得违背这些已确立的用户意愿。
